# ふるい分けの見積もりを、実際に arrange を回した結果に近づける

## きっかけ

ふるい分けは、記録から見積もった「badness の悪化を 3% に抑えて減らせる時間」（N と M）で比べ、Optuna の目的にもしている（docs/adr/judge-screening-by-time-saved.md）。この見積もりは記録を使ったシミュレーションで、実際に arrange を回した結果とは次の 2 点でずれる。

- N を arrange 自身の点数で測っていて、ベンチマークの badness ではない。
- モデルが別の手を採ったあとの図は記録にないので、記録どおりに進むとみなしている。見逃した改善が後のステップで取り戻せるかどうかは分からない。

Optuna はこの見積もりを最大にするので、ずれがモデルや候補の数によって変わると、実際には良くない設定を選んでしまう。

## 先に要るもの

実際の結果がないと、ずれを測ることも、補正を学ぶこともできない。そのため、本番と同じ形でモデルを動かす。

1. XGBoost のモデルを書き出し、決定木の評価を Rust で書く。本番で使うときにも要る。
2. arrange に、候補をモデルで絞る口を機能フラグで足す。
3. テスト用の図の 100〜200 枚を、いくつかのモデルと候補の数で実際に回し、badness と時間を測る。

## ML を使わずに済む部分

- 元の手順の最後の図の badness: ステップごとの記録（docs/adr/record-steps-for-replay.md）から最後の図を組み直せるので、正確に計算できる。N を badness で測るときの分母（全候補を評価したときの最後の badness）には、予測ではなくこの値を使う。
- 候補ごとの評価のあとの badness: 評価の結果の 1 つとして、記録の時に残せる。今の記録 v5 にはないので、取り直すか、再生で一部の候補だけ評価し直す。これがあれば、1 ステップの取りこぼしは予測ではなく実際の badness で測れる。

## 案

**A. 見積もりを実際の結果に合わせる補正モデル（採る）**

- 入力: 図ごとのシミュレーションの値（見積もった悪化、減る時間、途中で止まったか、取りこぼした回数）と、図の大きさ、候補の数。
- 出力: その図を、同じモデルと同じ候補の数で実際に arrange したときの badness の変化と時間。
- 学ぶ材料: 上の 3 で実際に回した結果。
- 点数と badness の違いと、違う手を採ったあとの影響の両方を、まとめて補正できる。
- 入力にはモデルの名前ではなく、シミュレーションの値（モデルの振る舞いを表すもの）を使う。名前を使うと、学んだモデル以外に当てはまらない。

**B. 見逃した手が後で拾われるかを予測する（作らない）**

シミュレーションの中でいちばん確かでない仮定を、直接学ばせる案。ただ、学ぶには A と同じく実際の結果が要り、A の補正モデルはこの影響もまとめて補正する。B を単独で作っても A より得るものはなく、実際の結果を集める手間は同じなので、作らない。

**C. 最初の修正と最後の仕上げの時間を、図の大きさから見積もる（採る）**

M にはこの時間が入っていない。トレースなしの本番の arrange を一部の図で回して、図の大きさからこの時間を見積もる回帰を作り、M に足す。実際の結果を集める準備を待たずに作れるので、A と並行して進める。

## 進める順

1. 上の「先に要るもの」の 1〜3 で、今のシミュレーションと実際の結果のずれを測る。
2. ずれがおおむね一定なら、1 つの係数で補正するだけにして、補正モデル（A）は作らない。
3. ずれが図やモデル、候補の数によって変わるときだけ A を入れる。最初は線形の回帰にし、足りなければ勾配ブースティングにする。

確かめるときの基準は、誤差の大きさより、モデルや候補の数の順位が実際と同じになるか（順位相関）にする。Optuna が使うのは順位だからだ。補正モデルを入れたあとも、Optuna の上位の試行は定期的に実際に回して確かめる。Optuna は補正モデルの誤差が有利に働く設定を選びやすいので、確かめないと、見積もりだけが良い設定に寄っていく。
