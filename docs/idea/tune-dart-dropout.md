# ふるい分けのモデルに、XGBoost の木のドロップアウト（DART）を試す

## きっかけ

ふるい分けのモデル（docs/adr/screen-as-top-3-yes-no.md）は、XGBoost の普通の勾配ブースティング（`gbtree`）で、木 400 本、学ぶ速さ 0.05、深さ 8 で学んでいる（nicevg-lab の `learn/classify.py` の `SETTINGS`）。行と列の抜き出し（`subsample`、`colsample_bytree`）は 0.8 にしている。

学習に使っていない図で、過学習を疑わせる結果が続いている。

- 設定を Optuna で探すと、探すときの値では上位の設定どうしの差が小さく、探すときに 1 番だった設定は取り分けた図で開始時の設定を下回った（docs/adr/screen-as-top-3-yes-no.md の「採らなかった案」、`learn/tune_time.py` の結果）。
- 特徴を足しても、モデルの上位 16 件に本来の手が入る割合は 7 割ほどで止まる（docs/adr/screening-features.md）。

勾配ブースティングでは、最初の数本の木が予測の大部分を決め、後の木は細かい残りを直すだけになりやすい（over-specialization）。後の木は学習用の図の細部に合わせがちで、学習に使っていない図では効かない。DART（Dropouts meet Multiple Additive Regression Trees、Rashmi & Gilad-Bachrach, AISTATS 2015）は、ニューラルネットのドロップアウトと同じ考え方で、木を 1 本足すたびに既存の木の一部を落としてから残りを学ぶ。これで木どうしが役割を分け合い、過学習が減ることがある。

## 案

XGBoost の木のモデル（今の `gbtree` のまま）に、ドロップアウトの設定を足して探す。XGBoost 3.4.1 では `booster="dart"` は非推奨で、`rate_drop` などを普通の木のモデルに直接渡す（`booster="dart"` を渡すと、そう警告が出る）。

| 設定 | 意味 | 探す範囲の目安 |
|---|---|---|
| `rate_drop` | 1 本足すたびに落とす木の割合 | 0〜0.3 |
| `skip_drop` | その回は 1 本も落とさない確率。落とさない回は、ドロップアウトのない今の学び方と同じ | 0〜0.7 |
| `one_drop` | `rate_drop` で 1 本も選ばれなかったときも、必ず 1 本は落とすか | 0 か 1 |
| `sample_type` | 落とす木を一様に選ぶか（`uniform`）、重みの大きい木ほど選ぶか（`weighted`） | 両方 |
| `normalize_type` | 新しい木と落とした木の重みの調整の仕方（`tree` か `forest`） | 両方 |

DART では落とす木があるぶん、同じ精度に木が多く要ることがある。木の数と学ぶ速さも一緒に探す。今の `subsample` と `colsample_bytree` も、行と列を落とす点で同じ方向の手当てなので、DART の設定と一緒に探し、どちらが効いたかを分けて見る。

良し悪しは、docs/adr/measure-screening-loss-by-real-runs.md の目的で決める。記録から見積もった M を 60% 以上に保ち、実際に回して測った悪化（悪くなった分だけ数えた平均）を小さくする設定を選ぶ。設定は nicevg-lab の `learn/folds.py` の分け方で、学習用の図の 5 つの組（同じプロジェクトのスケッチは同じ組）で選び、テスト用の図では最後に 1 回だけ測る。

### Rust 側で要るもの

なし。ドロップアウトの設定を付けて学んでも、保存される JSON は今と同じ `gbtree` の形で、木ごとの重み（`weight_drop`）も付かない（XGBoost 3.4.1 で、小さなデータで確かめた）。nicevg の `screening::Screen::from_xgboost_json` は、今のまま読める。

念のため、Python と Rust で予測が合うかは、`learn/check_screening.py` と同じ形で、記録の候補について余白（ロジット）の差を確かめる。

## 気になること

- **学習が遅くなる:** DART は、木を足すたびに落とした木を除いた予測を計算し直す。木が 400 本だと、普通の `gbtree` より何倍も遅くなりうる。1 試行で学ぶ時間が延び、実際に回して測る時間（数分）より長くなるかもしれない。
- **早期終了が使えるか分からない:** 木を足すたびに既存の木の重みを調整するので、途中で止めた時点のモデルが、その本数で学んだモデルと同じになるかは確かめていない。確かめるまでは、木の数は早期終了で決めず、設定として探す。
- **乱数で結果が揺れる:** 落とす木を乱数で選ぶので、乱数の種を変えたときの揺れが `gbtree` より大きいかもしれない。比べるときは種を複数にする。

## 進める順

1. Python だけで、ドロップアウトの代表的な値（`rate_drop` 0.1、`skip_drop` 0.5 など。XGBoost の既定値はどちらも 0 で、ドロップアウトしない）と今の設定を、5 つの組の交差検証で比べる。最初は記録から見積もる M と N で絞り、学習の時間も測る。
2. 差が出そうなら、上の表の設定を Optuna で探す。
3. 有望な設定が出たら、書き出したモデルを Rust の予測と照らし合わせ、実際に回して測る目的で比べる。
