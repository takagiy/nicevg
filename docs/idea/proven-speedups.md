# 結果を変えないことを Lean で証明しながら arrange を速くする

## きっかけ

経路探索のヒューリスティックの許容性を Lean で証明した（`proofs/NicevgProofs/Admissible.lean`）。同じやり方で、「出力を変えない」と証明できる高速化だけを入れていけば、スナップショットを一切変えずに arrange を速くできるのではないか、と考えた。

これまでの高速化の案（`docs/idea/screen-candidates.md`、`docs/idea/coarse-to-fine-route.md`）は、移動候補の順位や経路が変わりうるので、品質の測り直しが必要だった。出力が変わらないと証明できる変更なら、効果だけを測ればよい。

## 案

変更ごとに次の 3 つを揃える。

1. Lean の証明: 変更が結果を変えない理由を、探索や選択のモデルの上で定理として示す。Rust のコードがモデルの前提を満たすことは、コードを読んで確かめ、証明のファイルの冒頭に書く。
2. 出力の一致: `tests/fixtures` の 5 つの図と、`bindings/js/agent-sketches` のうちポートを使わない 14 個のスケッチで、変更の前後の SVG が一致することを確かめる。
3. 効果の計測: 同じ図で時間を測り、平均して速くなったものだけを採用する。

計測は `cargo run --release --example bench` で行う。候補どうしの比較は、候補を環境変数のフラグで切り替えられる 1 つのバイナリを作り、フラグだけを変えて 1 つずつ直列に走らせた。別々にビルドしたバイナリどうしの比較は、コードの配置の違いだけで ±2% 動く。

## 結果（2026-11-19）

### 採用した変更

倍率は変更の前後の時間の比で、1 より小さいほど速い。出力はどれも一致した。

| 変更 | 証明 | フィクスチャー 5 つ | スケッチ 14 個 |
|---|---|---|---|
| その場での引き直しの移動候補のうち、同じ辺を引き直すものは評価を 1 回で済ませる | `Shared.lean` | ×0.807（ER 図 ×0.642） | 未計測 |
| 経路探索で、同じ点・同じ向きに、屈折がより少なくより安い状態があれば、その状態を積まず展開もしない | `Dominance.lean` | ×0.964 | ×0.985 |
| 経路探索で、来た点への後戻りをしない | `BackStep.lean` | ×0.963 | ×0.983 |
| ポートの置き場所を選ぶとき、ポート間の距離が今の最良の経路のコスト以上の組は経路を探さない | `PrunedMin.lean` | ×0.986（ER 図 ×0.960） | 対象なし |
| ポートの置き場所は、ポート間の距離が近い組から先に試す | `AnyOrder.lean` | ×0.992（ER 図 ×0.976） | 対象なし |
| ラベルの置き場所は、クリアランスが今の最良のスコア以下なら、収まるかどうかの判定の前に外す | `Ceiling.lean` | ×0.997 | ×0.961 |
| 引き直す辺の両端がすべてポートに固定されているときは、サイドを選ばない | `Pinned.lean` | ×0.972（ER 図 ×0.917） | 対象なし |
| 辺の引き直しとラベルの移動のあとは、ノードを読み直さない | `Beside.lean` | ×0.952 | ×0.940 |
| viewBox を広げたあとは、図を読み直さず、viewBox の検査だけをやり直す | `Viewport.lean` | ×0.987 | ×0.978 |
| ノードを動かした移動候補では、動かしたグループの脇にあるノードを読み直さない | `Beside.lean` | ×0.981（ER 図 ×0.960） | ×0.965 |

ポートを使う図はフィクスチャーでは ER 図だけなので、ポートに関する 3 つの変更はほかの 4 つの図に影響しない。最初の変更と、ポートに固定された辺の変更、引き直しのあとのノードの変更は、別々にビルドしたバイナリどうしで比べた数字である。ほかは同じバイナリでフラグを切り替えて比べた。

上の 2 つの探索の枝刈りは効果が重なる。両方を入れたときは、フィクスチャーで ×0.964〜0.969、スケッチで ×0.958〜0.972 だった。片方にもう片方を足すと、フィクスチャーで 1.5〜2% 速くなる。

main と比べた全体の効果は「main との比較」の節に書く。

### 採用しなかった変更

| 変更 | 結果 | 理由 |
|---|---|---|
| 経路探索で、すでに届いた終点より優先度が高い状態を積まない | ×1.011 | 該当するプッシュは 0.6〜3% しかなく、判定のコストが上回る |
| 経路探索で、同じ点の別の向きに、ここで曲がっても安い状態があれば飛ばす | ×1.002（後戻りの枝刈りに足したとき） | 後戻りの枝刈りがほとんどを先に取っている |
| ポート間の距離の下限に、避けられない屈折のコストを足す | ×1.000 | 距離の下限だけで飛ばせる組がほとんど |
| ラベルのスコアの上限を、収まるかどうかの判定のあとで使う | ×1.000 | 重いのは収まるかどうかの判定のほうだった |
| 評価を共有するキーを、実際に引き直す辺の集合にする | ×1.033 | キーの計算が、増える共有より高くつく |
| サイドを選ぶ 2 回の探索で、1 回目のグリッドを取っておいて使う | ×1.023（スケッチ ×1.039） | グリッドを持ち続けると、配列を使い回すプールが空になり、確保が増える |
| A* のヒューリスティックを強める | 実装せず | 実際の残りコストとの差の大半は交差のコストで、数えるには終点からの逆向きの探索が要る。探索が展開するのはグリッド点の 4〜15% だけなので、割に合わない |
| arrange の移動候補を、得点の下限で評価の前に飛ばす | 実装せず | 得点の大半は fix してみないと分からない項で、下限（`Bound.lean`）が低すぎる |

### 調べて分かったこと

- A* のヒューリスティックは、4 つの図の約 2 億 7000 万本のリンクで一度も無矛盾性を破らなかった。同じ状態の展開し直しは全体の 0.00% だった。
- 経路探索の枝刈りで展開は 11〜15% 減るが、時間は 2〜4% しか減らない。飛ばせる状態は、展開しても隣への緩和がほとんど通らないからである。
- ER 図では、その場での引き直しの移動候補の 27% が、ほかの移動候補と同じ辺の集合を引き直していた。
- 親やラベルの多い図（C4 など）では、経路探索そのもの（25%）より、図の読み取りと検査（22%）、グリッドの構築（21%）のほうが重い。読み取りの再利用が効いたのはこのためである。

### main との比較

10 個の変更をすべて入れた状態を main（294d817）と比べた。時間は 5 ラウンドの最小で、出力の SVG はすべて一致した。

| 図 | main | 変更後 | 倍率 |
|---|---|---|---|
| c4-food-delivery-containers | 617.9 ms | 561.3 ms | ×0.908 |
| loan-origination-dfd | 1612.0 ms | 1476.8 ms | ×0.916 |
| order-checkout-dfd | 309.0 ms | 287.5 ms | ×0.930 |
| social-app-er | 3518.4 ms | 1623.9 ms | ×0.462 |
| storefront-architecture | 399.0 ms | 357.2 ms | ×0.895 |
| 合計 | 6456.3 ms | 4306.7 ms | ×0.667 |

5 つの倍率の平均は ×0.822、プロセスの CPU 時間の合計は ×0.643 だった。

スケッチ 14 個は、合計が 1204.3 ms から 1022.4 ms（×0.849）、倍率の平均が ×0.855 だった。14 個すべてが速くなり、倍率は ×0.793 から ×0.983 の間だった。

出力の一致は、計測に使わなかったポートなしのスケッチでも確かめた。のべ 115 個を main と変更後の両方で描き、SVG はすべて一致した（ほかに 9 個は 12 秒で打ち切り、比べていない）。ポートを使うスケッチは確かめていない。ポートに関する変更の出力は、ER 図のフィクスチャーとテストで確かめただけである。

## 証明が前提にしていること

- 証明は整数のモデルの上のもので、`f64` の丸め誤差は扱っていない。ポートの置き場所の下限には、丸めの分の余裕（1e-6）をコードの側で入れてある。
- 経路探索のモデルは、状態に「直前の 1 歩がどれだけ他の辺に並走したか」を含む。実際の探索は、この値が違う状態を 1 つにまとめ、安いほうだけを残す。枝刈りがこのまとめ方と組み合わさって経路を変えることは、モデルの上では否定できていない。例の図とテストでは出力は変わらなかった。
- 読み取りの再利用（`Beside.lean`、`Viewport.lean`）は、「ノードの読み取りは、ノードのグループの中と祖先だけを読む」「図の読み取りは viewBox を読まない」ことを前提にしている。読み取りのコードを変えるときは、この前提が保たれているかを確かめる。

## 次に試せること

- ノードを動かした移動候補の最初の読み取りで、辺とラベルも読み直さない。辺の読み取りは、シャフトと同じグループにあるポリゴンも読むので、「脇にある」の条件を辺ごとに決める必要がある。
- 検査（`inspect`）のうち、変わっていない辺やノードだけを読む検査の結果を引き継ぐ。
