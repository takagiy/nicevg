# ふるい分けは、badness の悪化を 3% に抑えて減らせる時間で比べ、評価する候補は決まった数で絞る

## 状況

ふるい分け（docs/adr/screen-moves-with-learning.md）で本当に知りたいのは、評価する候補を減らしたとき、badness の悪化を N%（今の目標は 3%）に抑えたまま、arrange の実行時間を何 % 減らせるか（M%）。それまでの比較や調整は、モデルの上位 16 件に本来の手（arrange が採った手）が入る割合や、最良の改善に届く割合を目的にしてきた。これらは時間を測っていない。候補を絞る方式も、モデルとは別に決めていた。

一方で、モデルを試すたびにすべての図で arrange を回すのは重い。

## 決定

記録から N と M を見積もり（nicevg-lab の `learn/sim.py`）、「N = 3% のときの M」を比べる値と Optuna の目的にする（`learn/tune_time.py`）。

時間の見積もり:

- **ステップの時間:** arrange は候補を並列に評価する（`evaluate_all`、重そうなものから、空いたスレッドが次を取る）。同じ並べ方で、評価する候補だけを T 本のスレッド（使う側のコア数の目安）に割り当て、各候補には記録の評価の時間（`eval_ns`）を使う。最後に終わる時刻をそのステップの時間とする。
- **ふるい分けの費用:** 全部の候補の特徴の計算（試しの引き直し `trial_ns` を含む）。これは候補を絞っても全部にかかる。
- **比べる元を本番に合わせる:** 記録では全部の候補を評価するが、本番の arrange は「前のステップで試して改善せず、その周りが変わっていない手」を評価しない（docs/adr/retry-only-moves-near-changes.md）。記録には各候補の前のステップの点数差と `touched` があるので、この省き方を再現する。再現しないと元が遅すぎて、M を大きく見積もってしまう。
- M = 1 −（モデルを使ったときの時間の合計）/（本番の省き方だけのときの時間の合計）。最初の修正と最後の仕上げの時間は入れていないので、M は「ステップの時間のうち減らせた割合」。

悪化の見積もり:

- ステップごとに、「最良の候補の点数差」と「評価した候補の中で最良の点数差」の差を、取りこぼしとして足す。
- 改善する手を 1 つも評価できないのに、ほかに改善する手があるステップでは、arrange がそこで止まるとみなし、それ以降の改善をすべて失ったとする（それ以降の時間もかからない）。
- 図ごとに、取りこぼしの合計を、全部の候補を評価したときの最後の点数（arrange 自身の点数）で割る。N はその図ごとの値の平均で、90 パーセンタイルも並べる。

候補を絞る方式は、決まった数 k にする。Optuna の 1 回の試行では、モデルを学び、検証用の図（学習用の図の一部）で k を動かして N と M の組の線を描き、N = 3% のときの M を線の上で補間して目的の値にする。k はここで決める。最後に、どの試行も使わなかった図（学習用の図の別の一部）で、その k で 1 回だけ測る。同じ図で決めて測ると良く見えすぎるからだ。

## 結果

記録 v4（v3 に、最初の `--grow` の図 966 枚を足したもの）のテスト用の 785 図で、スレッドを 16 本、モデルを上位 3 件の 2 択（docs/adr/screen-as-top-3-yes-no.md）、乱数の種を 1 つとして見積もった。N を一定に抑えたときの M（候補の絞り方のうち一番良いもの。どれも決まった数だった）:

| | N = 1% | N = 3% |
|---|---|---|
| ランダムな順 | 届かない | 56.5% |
| 25 個の特徴 | 60.2% | 74.2% |
| ＋ 記録から計算できる 9 個 | 62.0% | 75.1% |
| ＋ さらに下書きの形から計算できる 14 個 | 60.1% | 74.6% |

得たもの:

- モデルの効果を時間で表せる。N = 3% でランダムな順より 18 ポイントほど多く時間を減らせる。N = 1% には、ランダムな順だと各ステップで 64 件評価しても届かない（そのときの N は 2.5%）。
- 絞り方の比べ方が変わった。決まった数（各ステップで評価する候補の数。N = 3% で 24〜26 件、N = 1% で 48 件ほど）が一番良く、候補の数に比例させる方式（N = 3% での M が 55%）と、確率の合計で決める方式（同じく 51%）を上回った。候補の多いステップに多く割り当てる方式は、評価に一番時間がかかるステップで多く評価してしまう。

失ったもの:

- 見積もりは記録を使ったシミュレーションで、本物とずれる。N は arrange 自身の点数で測っていて、ベンチマークの badness ではない。モデルが別の手を採ったあとのステップは、記録どおりに進むとみなしている。ずれを本物で確かめる案は docs/idea/check-estimates-against-real-runs.md にある。
- 評価する件数が少ないと、N の 90 パーセンタイルがとても大きい（25 個の特徴で各ステップ 2 件だけ評価すると、N の平均 21% に対して 90 パーセンタイルは 60%）。改善する候補を 1 つも評価できないステップで arrange が止まり、その後の改善を全部失う図があるため。
- M の上限は 92% ほど。特徴（試しの引き直しを含む）を全部の候補で計算する費用が残る。1 ステップの候補が 64 件を超えることは多く、決まった数を 64 件にしても、ステップの時間は半分ほどになる。
- 特徴を足したときの M の差は 1〜2 ポイントで、乱数の種が 1 つ、信頼区間もまだないので、差は確かではない。見逃した手を次のステップで評価したら拾い直したとみなしても、M は 0.5〜1.5 ポイントしか変わらない。

## 採らなかった案

- **上位 k 件に本来の手が入る割合で比べる:** 時間を測っていない。下の「試す数を確信度で変える」のように、試した候補の数で比べると良く見える方式が、時間で比べると負けた。
- **候補の数に比例させる:** k = max(k_min, ⌈r·n⌉)。苦手の大部分が候補の多いステップだった（docs/idea/screening-weak-spots.md）ので試したが、上の結果のとおり、決まった数を下回った。
- **試す数を確信度で変える:** 候補をモデルの順に 16 件（スレッドの数）ずつ評価し、残りを試す価値がなくなったら止める。止め方は、一番良い手である確率の合計で止める（案 1）、楽観的な見積もり（分位点回帰の下側）で止める（案 2）、順位モデルの点数の差で止める（案 3）の 3 つを試した（`learn/adaptive.py`）。試した候補の割合で比べると、同じ割合で本来の手を拾う割合が、決まった数より 3〜4 ポイント高かった。たとえば案 3 でしきい値を 4.0 にすると、候補の 47% を試して本来の手の 95% を拾った（決まった数では 56% を試す必要がある）。しかし時間で比べると、確率の合計で止める方式の M は N = 3% で 51% にとどまり、決まった数の 74% を下回った。記録 v5 で方式を増やして比べ直しても、決まった数を確かに上回るものはなかった（docs/idea/vary-candidate-count.md）。
