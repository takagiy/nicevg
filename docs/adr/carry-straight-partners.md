# 曲がった辺や交差する辺を直すためのずらしがまっすぐな辺を折ったら、その辺の先のノードも一緒に動かして試す

## 状況

issue #59 の再現例は、0.31.5-beta.39（[サイドの選択で、向かい合うサイドを、重なりの中央から 10px ずつ離れた線でも見積もる](side-choice-off-middle-lines.md)）で from → to がまっすぐになった代わりに、次のものを失った。

- 報告と同じ文字幅: c → to が from → d と交差する（交差 0 → 1）。
- 狭い文字幅（from の半径 33px、to と d の半径 56px、c の半径 65px）: to → g が Z 字になる（屈折 8 → 9）。

調べた結果、原因は次のとおりだった。

1. b と c から to への辺は、d の下を通らない限り from → d と交差する。2 本とも d の下を通すと、to の下のサイドに b → to、c → to、d → to が集まり、to → g は to の右から出る。to が下書きの高さにあると、to の右から g へ向かう線に、to のすぐ右のボックス f がかかり、to → g は Z 字になる。
2. from と to をともに 40px 下げた配置なら、両方の文字幅で交差は 0、to → g の屈折は 1 になる。この配置をスケッチに書いて描くと、レイアウトはこの配置を保つ。
3. レイアウトは、この配置に届かなかった。from と to はまっすぐな辺で結ばれているが、円の大きさが違うので中心の高さがずれ、行としてまとめて動かす移動候補（`lines`）にならない。to だけを 40px 下げると、from → to は上 → 上の U 字に折れる。
4. from と to をまとめて下げても、2 つのノードの辺 9 本をまとめて再経路探索する。サイドを選ぶときは、一緒に再経路探索する辺の経路を見ない（[意図が伝わらない段階の問題が残った辺は、1 本ずつ引き直す](reroute-lost-edges-one-at-a-time.md) と同じ理由）。そのため b → to と c → to が from → c と from → d を越えて to の下へ入り、交差する。この移動のスコアの改善は −162.4 にとどまり、to を左へ 40px 動かす移動候補（−488.2）に負けた。
5. まとめて下げた状態から、さらに 20px 下げる移動も試される。その移動では b → to が d の上を越えて短くなる代わりに from → d と交差し、スコアはこれを良い（−135）とした。

一方、まっすぐな辺の先のノードが背の高いノードなら、ずらしたノードだけを動かしても、その辺はまっすぐなまま別の高さへ移れる。ターミナルサイドバーの DFD の 6.2 は、背の高い hc2 と user にまっすぐな辺でつながり、main は 6.2 だけを 40px 下げて、6.1 → 6.2 の屈折を 2 回にしている。

## 決定

1. 2 回以上折れる辺か、ほかの辺と交差する辺を持つノードを 1 つだけずらす移動候補のうち、まっすぐだった辺を折ったものがあれば、スコアが最も良い 1 件を、折れた辺の先のノードも一緒に動かす移動としてもう一度評価する。1 つだけずらす移動候補はそのまま残す。
2. 一緒に動かす移動で、動かしたノードの辺どうしが交差したら、ノードごとに辺をもう一度再経路探索する。ノードの順は、ずらしたノードを先にした順とその逆の 2 通りを試し、スコアが最も良く、問題を増やさない結果を採る。
3. 移動は、問題とジョグに加えて、交差も増やさない（経路探索の数え方で、移動前の状態と比べる）。

## 結果

テストのフィクスチャの 6 つの図（Apache Druid を除く）、#58 のスケッチ、#59 の再現例（両方の文字幅）を、1 つずつ描いて比べた（0.31.5-beta.39 → 変更後）。時間は 6 つの図の合計で、3 回測った。

| #59 の再現例 | beta.39 | 変更後 |
|---|---|---|
| 報告と同じ文字幅: 交差 | 1 | 0 |
| 報告と同じ文字幅: 屈折 | 7 | 8 |
| 狭い文字幅: Z 字 | 1（to → g） | 0 |
| 狭い文字幅: 屈折 | 9 | 8 |

| 6 つの図 | beta.39 | 変更後 |
|---|---|---|
| 経路が変わった辺 | ― | 0 / 192 |
| 問題 | 0 | 0 |
| 合計時間 | 7.10、6.99、6.85 秒 | 8.04、8.06、8.04 秒 |

得たもの:

- #59 の再現例は、両方の文字幅で同じ配置（from と to を 40px 下げ、to を左へ 60px）になる。交差も Z 字もない。b → to と c → to は d の下を通り、to → g は f の下を通って 1 回だけ折れる。
- 6 つの図と #58 のスケッチでは、経路が 1 本も変わらない。

失ったもの:

- 6 つの図の合計時間が 13〜17% 増えた。一緒に動かす移動は、ほかの移動候補の評価が終わってから 1 件だけ評価するので、並列に評価されない。もう一度の再経路探索は、修正のステップを最大 4 回足す。
- 交差を増やさない決まりは、移動ごとに移動前の状態と比べる。図の最後の交差が beta.39 以下になることは保証しない。
- #59 の再現例（報告と同じ文字幅）の屈折が 7 → 8 に増えた（beta.38 の 9 以下）。
- #59 の再現例で、from の右から 3 本が並んで出る状態は残る。from → c を from の下から出すと、下、右、下と 2 回折れる Z 字になる（サイドの選択の見積もりで、右 → 上の 504.5 に対して下 → 上は 585.0）。屈折 1 回で下から出す経路は、from の真下の b がふさぐ（下 → 左は 824.5、屈折 3）。変更後の配置から b、c、d のどれか 1 つを各軸 −60〜60px 動かした 144 通りでも、from の右を 2 本以下にした配置は、両方の文字幅のどちらかで交差か Z 字が増えるか、from → to が折れた。

## 採らなかった案

- 曲がった辺や交差する辺を持つノードをずらす移動候補を、最初から、まっすぐな辺の先のノードも一緒に動かす移動に置き換える: #59 は直るが、6 つの図で 50 本の経路が変わり、時間が 26% 増えた。ターミナルサイドバーの DFD では、6.2 だけを下げる移動がなくなり、6.1 → 6.2 の屈折が 2 → 3 に増えた。ソーシャルアプリの ER 図で交差と Z 字が 1 つずつ、融資審査 DFD と注文チェックアウトの DFD で屈折が 1 つずつ増えた。
- 置き換えずに、1 つだけずらす移動候補と一緒に動かす移動候補の両方を、最初から評価する: 6.2 と #59 は直るが、時間が 52% 増えた。
- まっすぐな辺の今の線が、ずらしたノードのサイドの範囲から外れるときだけ一緒に動かす: 6.2 から user への辺の線（y = 955）が外れるので、6.2 を 1 つだけ下げる移動は戻らなかった。
- まっすぐな辺を折ったずらしすべてについて、一緒に動かす移動を評価する: 時間が 64% 増えた。
- もう一度の再経路探索を、複数のノードを動かす移動候補すべて（揃った行や列を含む）に行う: 揃った行や列はノードが多く、修正のステップをノードの数の 2 倍、順に回す。融資審査 DFD の時間が 1.76 → 3.61 秒になった。
- サイドの選択を局所的に変える（3 回目のサイドの選択、サイドの選択の屈折のコストを 40 にする、サイドを譲り合った辺の組み合わせを比べる）: どれも、両方の文字幅で #59 を直せなかった。6 つの図で 19〜46 本の経路が変わり、狭い文字幅の #59 で交差が 0 → 1 に増えた。
- 交差のコストを 300 から 350 か 450 に上げる: 報告と同じ文字幅の #59 は直るが、狭い文字幅の to → g の Z 字は残る。6 つの図で 56 本か 83 本の経路が変わり、屈折が 17 か 16 増えた。450 では融資審査 DFD の交差が 3 → 5 に増えた。
- まっすぐな辺の両端を一緒に動かす移動候補を、ずらす移動候補とは別に、まっすぐな辺ごとに足す: #59 は直るが、6 つの図で時間が 42〜115% 増え、25〜47 本の経路が変わった。
- もう一度の再経路探索を 1 通りの順だけで行う: ノード名の逆順（#59 では to が先）だけが #59 を直した。ずらすノードを先にする順と、辺の交差が多いノードを先にする順では、報告と同じ文字幅の交差が残った。ノード名の順には根拠がないので採らない。
- 交差する辺を 1 本だけ、交差を 10 倍に見積もって再経路探索する移動候補を足す: c → to を d の下に通す経路は見つかるが、スコアは +144.4 悪くなり、採られない（c → to の経路 +253、to の下のサイドの端点の間隔 +112.7、b → to との並走 +60、交差 −300）。
