# 意図が伝わらない段階の問題が残った辺は、1 本ずつ引き直す

## 状況

引き直す辺は、経路を引く前に、接続するサイドを選ぶ。このとき見るのは、すでに経路が決まっている辺だけで、一緒に引き直す辺の経路は見ない。そのため、手前の隙間に収まる本数より多くの辺が、同じサイドを選ぶことがある。経路が見つからなかった辺は直線で引かれ、斜めの辺、ノードの貫通、サイドに沿う辺になる。

そこで、引き直した後に意図が伝わらない段階の問題（CRITICAL）が残った辺を、もう一度引き直している。2 回目は、ほかの辺の経路を見てサイドを選び直せる。

この再試行は、残った辺をまとめて引き直していた。まとめた辺どうしは、また互いの経路を見ずにサイドを選ぶので、同じノードのまわりで 2 本以上が残ると、再試行の中で同じ問題が起きる。テキストの幅を実測に変えたとき、Apache Druid のアーキテクチャ図で 5 本が同時に残り、`edge-43` が斜めのまま残った。

## 決定

残った辺を、図の辺の順に 1 本ずつ引き直す。先に引き直した辺の経路によって問題がなくなった辺は、引き直さない。

## 結果

親を持つ 49 個のスケッチを、1 つずつ計測した（テキストの幅を実測にした直後の状態）。

| | まとめて | 1 本ずつ |
|---|---|---|
| 問題の数 | 241 | 220 |
| うち意図が伝わらない段階 | 138 | 126 |
| 処理時間の合計 | 842 秒 | 909 秒 |

得たもの:

- 意図が伝わらない段階の問題が 138 → 126 に減った。
- Apache Druid の図の一部を切り出した fixture で、斜めの辺とノードの貫通がなくなった。
- 4 個のスケッチで問題が減った（Apache Druid 51 → 38、OpenSearch 31 → 24、PostgreSQL の SELECT 13 → 6、Sentry 7 → 0）。

失ったもの:

- 処理時間が 8% 増えた。
- 4 個のスケッチで問題が増えた（GitHub ARC 14 → 21、Apache Kafka 0 → 3、NCBI GEO 0 → 2、Drupal 2 → 3）。増えたのは、ラベルの配置の問題である。問題が 0 個のスケッチは 21 個 → 20 個になった。
- 残った辺が同じサイドに集まるとき、それらの端点を一度に均等に並べられなくなった。後から引き直す辺は、先に引き直した辺が残した位置に入る。これはコードの仕組みから言えることで、見た目に差が出る図は確認していない。

## 採らなかった案

- まとめて引き直す（従来の方式）: 上の表のとおり。同じノードのまわりで 2 本以上が残ると、再試行の目的（ほかの辺の経路を見てサイドを選び直す）を満たさない。
- まとめて引き直した後、まだ残っている辺を 1 本ずつ引き直す: 問題の数 247、意図が伝わらない段階 143、処理時間 831 秒。まとめて引き直す方式と比べて、問題が減ったスケッチは 0 個、増えたスケッチは 2 個だった。
