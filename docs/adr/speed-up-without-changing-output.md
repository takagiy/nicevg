# arrange の高速化は、出力を変えないものに限る

## 状況

品質スナップショットの badness が 4 つの例の図のどれでも 3% 以上悪くならない範囲で、arrange をさらに 20% 速くしたかった。

速くする方法は 2 種類あった。1 つは、選ぶ手や引く経路は今のままで、同じ計算を軽くするもの。もう 1 つは、評価する候補を減らしたり探索を粗くしたりして、計算そのものを省くもの。後者のほうが効果は大きい。

ところが、後者は経路や選ぶ手を少しでも変えると、badness が大きく揺れた。arrange の採点（`Context::score`）と badness は重みが違う。採点は迂回の長さや曲がりの数を重く見るが、人の判断から決めた badness はジョグ・3 つ目以降の曲がり・交差を重く見る。そのため、採点の上ではほぼ同じ選択でも、badness では数 % 違う。さらに、1 つの手や経路が変わると、配置改善のその後の道筋がまるごと変わる。

## 決定

arrange を速くする変更は、4 つの例の図の出力がバイト単位で変わらないものに限る。速さは前のコミットと交互に測った実時間と CPU 時間の中央値で、出力は v0.14.0 の出力との一致で確かめる。

今回採ったのは、どれも出力を変えないものだった。

- A* の計算を軽くした: 見積もりで終点を並べ替えない、待ち行列の項目を整数 1 つにする、距離の表を小さくする。
- メモリの確保と書き込みを減らした: 格子の配列の型を小さくする、配列と待ち行列をスレッドごとに使い回す、変更履歴を古い分と共有する、採らなかった候補を裏のスレッドで捨てる。
- 候補を重そうな順にスレッドへ配った。

経緯と数字は docs/idea/lighter-search-and-flow.md にある。

## 結果

得たもの:

- arrange が実時間で 24〜32%、CPU 時間で 21〜25% 速くなった（融資審査 DFD 2.78 → 2.00 秒、注文 DFD 0.78 → 0.53 秒、ストアフロント 0.90 → 0.65 秒、C4 0.97 → 0.73 秒）。
- 出力が変わらないので、badness も品質スナップショットも変わらない。速くするたびに画像で確かめ直す必要がない。

失ったもの:

- 効果の大きい方法を使えない。遅延評価の貪欲法は、それだけで 31〜40% 速くなった。
- 出力を変えない範囲の工夫は、データの持ち方やメモリの使い方の細かい調整が中心で、コードが増えた（使い回しのための置き場、整数に詰めた待ち行列の項目、共有する変更履歴など）。
- 速さを大きく伸ばす余地は小さくなった。この CPU（8 コア 16 スレッド）では、計算を減らしてもメモリの読み書きで頭打ちになる。

## 採らなかった案

- 遅延評価の貪欲法（前のステップで評価した手の改善量を見込みに使い、見込みの高い順に評価して打ち切る）: ストアフロントと注文 DFD で選ぶ手が変わり、badness が 4〜5% 悪化した。変わった場所の近くの候補を評価し直すと、範囲を広く取らない限り悪化が残り、広く取ると今より遅くなった。全候補の改善量を記録して打ち切り規則を模擬したが、どの規則でも同じ手を選び続けられなかった。
- 重み付き A*（見積もりを 1.2 倍・1.5 倍）: 最適でない経路が混じり、badness が最大 28% 悪化した。修正のパス数が増え、融資審査 DFD では 70〜178% 遅くなった。
- 格子の値を点ごとの構造体 1 本にまとめ直す、bool の配列をビット列にする: 出力は変わらないが、どちらも遅くなった。A* が触るのは格子のごく一部で、全体をまとめ直す手間やビット演算のほうが重かった。

出力を変える高速化を使えるようにするには、先に arrange の採点を badness に近づける必要がある。そうすれば、採点の上で同じくらい良い選択が、badness の上でも同じくらい良くなる。
