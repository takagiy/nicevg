# テキストの幅は、マシンのフォントでシェーピングして測る

## 状況

テキストの幅は見積もっていた。ワイドな文字（漢字、かななど）はフォントサイズの 1 倍、それ以外の文字は 0.59 倍である。

この見積もりは、実際に描かれる幅より広かった。Windows のフォントで測った幅に対して、Arial で 1.26 倍、Meiryo で 1.15 倍、Consolas で 1.07 倍である。ラベルの範囲が実際の文字より広いので、実際には重なっていないラベルが、問題として報告されていた。TypeScript の `text()` も同じ見積もりを使うので、スタイルが描くノードも、テキストに必要な大きさより広かった。

## 決定

テキストの行を、宣言された `font-family` と `font-weight` のフォントでシェーピングして、その幅を使う。

- シェーピングとフォントの選択は `parley`、マシンのフォントの検索は `fontique` に任せる。CSS の `font-family` の並びの解釈と、`sans-serif` などの総称名からフォントを選ぶ処理も、これらのクレートが行う。
- Liberation Sans（Regular と Bold、SIL OFL 1.1）をライブラリに同梱する。総称名に当たるフォントがマシンにないとき、このフォントで測る。
- 環境変数 `NICEVG_SYSTEM_FONTS=0` で、同梱のフォントだけで測る。どのマシンでも同じ幅になるので、テストはこの設定で実行する。
- どのフォントにもグリフがない文字は、Unicode の East Asian Width が定める桁数で幅を決める。1 桁をフォントサイズの 0.5 倍とする。ワイドな文字と絵文字は 2 桁、結合文字は 0 桁である。桁数は `unicode-width` クレートで求める。宣言のフォントにないかなと漢字も、のちに [桁数で測るようにした](kana-and-han-by-columns.md)。
- TypeScript の `text()` も、ネイティブライブラリに同じ計測を頼む。スタイルが描く間に作ったテキストは、`rootAttrs` の `font-family` と `font-weight` で測る。`nicevg doc` と `nicevg run` のスクリプトはサンドボックスの中で動くので、ホストが計測の関数を渡す。

## 結果

親を持つ 49 個のスケッチを、Windows のフォントで、1 つずつ計測した。「変更後」には、同じ時期に入れた 2 つの変更（[問題が残った辺を 1 本ずつ引き直す](reroute-lost-edges-one-at-a-time.md)、[端点が移った後に並べ直す](spread-ends-after-a-side-move.md)）も含まれる。

| | 変更前 | 変更後 |
|---|---|---|
| 問題の数 | 380 | 266 |
| うち意図が伝わらない段階 | 223 | 146 |
| `edge-near-label` | 126 | 84 |
| `label-overlaps-node` | 92 | 56 |
| `edge-label-detached` | 78 | 57 |
| `label-overlaps` | 31 | 13 |
| 問題が 0 個のスケッチ | 14 | 19 |
| 画像の面積（中央値の比） | 1 | 0.91 |
| 処理時間の合計 | 916 秒 | 994 秒 |

得たもの:

- ラベルの範囲が、実際に描かれる文字の範囲と合うようになった。ラベルの配置の問題が減った。
- 図が小さくなった。TypeScript の `text()` を実測にした段階で、ノード 1128 個のうち 960 個が狭くなった。
- 幅の狭い文字（`i`、`l`）と広い文字（`m`、`w`）、太字と標準の違いが、幅に反映される。

失ったもの:

- 結果が、実行するマシンのフォントで変わる。同じ入力でも、マシンが違えば配置が変わりうる。`NICEVG_SYSTEM_FONTS=0` を設定すれば同じになるが、その幅は Liberation Sans の幅である。
- 表示するマシンのフォントが、測ったマシンのフォントと違えば、幅は一致しない。これは見積もりでも同じだった。
- 依存が増えた。`Cargo.lock` のパッケージは 77 個から 138 個になった。Windows 用のライブラリは 7.3MB から 18.6MB になった。同梱のフォントは 2 つで 0.8MB である。
- `nicevg doc` と `nicevg run` の親プロセスが、ネイティブライブラリを読み込むようになった。これまでは、レイアウトを行う子プロセスだけが読み込んでいた。
- TypeScript の `text()` を実測にした段階で、問題の数が 202 から 266 に増えた（増えたスケッチ 16 個、減ったスケッチ 14 個）。増加の大きい 8 個のうち、5 個では画像の面積が 0.82〜0.88 倍に縮んだが、2 個では縮んでいない。原因は調べていない。
- スタイルの外で作った `text()` は、`rootAttrs` のフォントでは測られない。`font-family` を宣言しないテキストとして測られる。
- グリフがない文字のうち、桁数が言語によって変わる文字（①、※ など）は 1 桁になる。日本語のフォントはこれらを 1em で描くので、狭く測られる。のちに [2 桁と数えるようにした](kana-and-han-by-columns.md)。

## 採らなかった案

- 文字ごとの幅の表を持つ: 依存が増えず、どのマシンでも同じ結果になる。しかし、Arial に近いフォントにしか合わず、kerning が入らない（Arial で ±5% の誤差）。ASCII 以外の文字は見積もりのまま残る。
- `ttf-parser`、`rustybuzz`、`fontdb` を組み合わせて測る: `font-family` の並びの解釈と、総称名からフォントを選ぶ処理を、自分で書く必要がある。
- グリフがない文字のために、日本語のフォントを同梱する: パッケージが数 MB から十数 MB 増える見込みである（計測していない）。日本語以外の文字には効かない。
- グリフがない文字を、そのまま「グリフなし」の記号の幅で測る: Liberation Sans では 0.75em になる。日本語のフォントがないマシンで、日本語のラベルが 25% 狭く測られる。
