# 良くならなかった移動は、変わった場所から離れていれば次のレイアウトのラウンドで試し直さない

## 状況

例の図（C4、融資審査 DFD、注文 DFD、SNS の ER 図、ストアフロント、README の `docs/images/before.svg`）のどれでも badness が 3% 以上悪くならない範囲で、arrange を 20% 速くしたかった。

arrange はレイアウトのラウンドごとに移動候補を作り、移動候補ごとに修正を 1 ステップ回して比べる。ラウンドは最大 12 回あり、毎回ほぼ同じ移動候補を 1 から評価し直していた。どの図でも、1 ラウンドで良くなる移動候補は一部だけで、残りは前のラウンドでも良くならなかった移動候補だった。

速さを測ると、時間はほぼすべて移動候補の評価にかかっていた。評価は全コアで並べて回すので、図の大きさで効き方が違った。

- 大きい図: 評価の CPU 時間そのもの。
- 小さい図: 評価の CPU 時間に加えて、ラウンドごとにスレッドを作り直す待ち時間。`before.svg` では、1 ラウンド約 6ms のうち最大 1ms がスレッドの起動待ちだった。

docs/adr/speed-up-without-changing-output.md のとおり、出力を変えないことを条件にした。

## 決定

次の 4 つを入れた。

- **試し直す移動候補を絞る**（`src/layout.rs`）: 次の 2 つが両方そろった移動候補は試し直さず、前の点数を引き継ぐ。
  1. 前のラウンドで良くならなかった、または問題やジョグが増えるので外された。
  2. そのラウンドで採った移動が変えたもの（ノード、ラベル、セグメント）が、移動候補の届く範囲に 1 つも触れていない。

  届く範囲は、移動候補が動かすノードと、そのノードにつながる辺の各セグメントを、`MOVE_REACH`（20px）ずつ広げた四角の集まり。初めて出てきた移動候補と、前のラウンドで良くなった移動候補は必ず試す。
- **スレッドを使い回す**: 評価用のスレッドは arrange の最初に 1 回だけ作り、各ラウンドの移動候補をキューで渡す。
- **サイドの選び直しを省く**（`src/fix.rs`）: 辺を出すサイドは、ほかの辺が選んだサイドの混み具合を見て 2 回選ぶ。2 回目は混み具合が増えるだけなので、1 回目に選んだサイドの増え方がそのノードで一番小さければ、2 回目も同じサイドが一番安い。そのときは 1 回目の結果を使う。
- **ポートの置き場所の候補を 1 回ずつ計算する**: 置き場所を比べる `min_by` が、比べるたびに両方の経路を引き直していた。

## 結果

得たもの:

- 6 つの例の図で、arrange が実時間で 36〜49% 速くなった。直前のコミットと 3 回ずつ交互に測った中央値（2026-10-17、8 コア 16 スレッド）:

  | 図 | 前 | 後 |
  |---|---|---|
  | C4 | 770 ms | 488 ms |
  | 融資審査 DFD | 2075 ms | 1225 ms |
  | 注文 DFD | 593 ms | 305 ms |
  | SNS の ER 図 | 5559 ms | 3311 ms |
  | ストアフロント | 792 ms | 405 ms |
  | `before.svg` | 30.5 ms | 17.9 ms |

- 6 つの図の出力は変わらない。品質スナップショットも、badness も同じ。

失ったもの:

- 移動候補を絞る仕組みは、出力が変わらないことを例の図でしか確かめていない。「周りが変わっていなければ結果も変わらない」は見込みで、どの図でも正しいとは言えない。ほかの図では、本来効く移動を飛ばして結果が悪くなることがありうる。
- `MOVE_REACH` は例の図で測って決めた値で、根拠は測った結果だけ。10px では `before.svg` の badness が 3.22% 悪くなった。15px と 20px では変わらなかった。
- サイドの選び直しを省くと、コストがちょうど同点のときに、2 回目なら選んだはずの別のサイドを選ぶことがありうる。
- arrange を 1 回呼ぶたびに、移動候補の数にかかわらず、論理コアの数だけスレッドを作る。
- コードが増えた。移動候補ごとの点数の記録、変わった場所と届く範囲の計算、スレッドのキュー。

## 採らなかった案

- **届く範囲をもっと狭くする（0px、5px、10px）**: `before.svg` がさらに 32〜38% 速くなったが、badness が 3.22% 悪くなった。
- **最後の経路も、粗いグリッドで決めた通り道の中だけで探す**: SNS の ER 図と C4 が 34〜36% 速くなった。一方で、badness が SNS の ER 図で 16%、ストアフロントで 8% 悪くなった。融資審査 DFD は逆に 37% 遅くなった。
- **同じ入力の経路探索をキャッシュする**: SNS の ER 図では経路探索の 55% が前と同じ入力だった。ほかの図では 1〜2% しかなく、効くのは ER 図だけだった。
- **サイドの選び直しを、混み具合がまったく同じときだけ省く**: 結果は確実に同じになる。ただ、同じ点を動かす移動候補では、ほかの辺のサイドが必ず混み具合に入るので、条件がそろうことがほとんどない。2 回目の呼び出しは 1% しか減らなかった。
- **前の点数の順に評価して途中で打ち切る（遅延評価の貪欲法）**: docs/adr/speed-up-without-changing-output.md で試し、badness が悪くなった。今回は打ち切らず、良くならなかった移動候補だけを、変化が届いていないときに限って飛ばす。こうすると、良くなる見込みのある移動候補は毎回試す。
